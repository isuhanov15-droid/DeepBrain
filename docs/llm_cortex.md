# LLM Cortex v1

## Назначение

LLM Cortex — асинхронный наблюдательный слой над автономным ядром DeepBrain. Он получает ограниченный снимок состояния и контекст долговременной памяти, после чего возвращает интерпретацию, внутреннюю речь, вопрос к памяти и оценку риска.

LLM не выбирает действие, не вызывает `Actuator`, не меняет `ActionSelector`, не обходит action mask и не пишет непосредственно в память. Если в дальнейшем наблюдения Cortex будут влиять на поведение, это влияние должно проходить через отдельный валидатор намерений и существующую политику безопасности.

## Контракт

Версия входного и выходного контракта: `deepbrain.cortex.v1`.

Ответ модели обязан содержать ровно пять полей:

```json
{
  "interpretation": "Краткая интерпретация состояния",
  "inner_speech": "Безопасная внутренняя речь",
  "memory_question": "Вопрос к долговременной памяти",
  "risk_level": "low",
  "confidence": 0.8
}
```

Неизвестные и пропущенные поля, обрезанный JSON, неверный `risk_level`, нечисловая или выходящая за `[0,1]` уверенность отклоняются. Ответ, ставший старше `maxStalenessTicks`, не публикуется.

## Ollama

Первая реализация использует `/api/chat` Ollama и модель `qwen3.5:4b-q4_K_M`. Запросы выполняются по одному, вне тика `LifeLoop`, с тайм-аутом и ограничением размера ответа. В Ollama передаётся не полный `CognitiveFrame`, а три короткие семантические строки:

- `state` — сценарий, настроение, безопасность, боль, возбуждение, мотив, решение и награда;
- `events` — только машинный тип, тяжесть, значимость и признак обработки последних событий, без verbose JSON и текстового payload;
- `memory` — число воспоминаний, сходство, полезное/вредное действие, уверенность и агрегированный опыт сценария, без списка доказательных эпизодов.

Служебные `contractVersion`, `frameId`, `tick` и `timestamp` остаются в Host и не расходуют контекст модели. Полный человекочитаемый вывод `memory.explain` остаётся доступен оператору, но не включается в LLM prompt.

Пример конфигурации:

```json
"llm": {
  "enable": true,
  "provider": "ollama",
  "baseUrl": "http://127.0.0.1:11434/",
  "model": "qwen3.5:4b-q4_K_M",
  "autoObserve": true,
  "observeEveryTicks": 300,
  "timeoutSeconds": 120,
  "maxStalenessTicks": 600,
  "numPredict": 128,
  "temperature": 0.1,
  "keepAlive": "5m",
  "maxMemoryLines": 2,
  "maxRecentEvents": 2,
  "maxContextChars": 96
}
```

При скорости 5 тиков/с интервал 300 означает один автоматический запрос примерно в минуту. На слабом CPU интервал следует увеличить так, чтобы обычная задержка модели была меньше окна устаревания.

`numPredict=128` рассчитан на пять коротких полей контракта. `maxMemoryLines`, `maxRecentEvents` и `maxContextChars` задают бюджет входного контекста; увеличивать их следует только после измерения `promptTokens` и времени prompt evaluation.

## Диагностика

- `llm.status` — конфигурация, текущий frame/возраст, счётчики, wall-clock latency, размер JSON и сводные метрики Ollama.
- `llm.observe` — поставить ручное наблюдение в очередь.
- `llm.last` — последний принятый структурированный ответ вместе с метриками `requestBytes`, `promptCharacters`, `dataCharacters`, `promptTokens`, `outputTokens`, временем загрузки, обработки prompt и генерации.
- Событие внешнего API `cortex.insight` — тот же принятый ответ в универсальном конверте.

Для измерения скорости сначала выполняется один прогревочный запрос, затем второй. Диагностически важны две разные величины: `latency` — полное время глазами DeepBrain, `metrics.totalSeconds` — время Ollama. Разница указывает на ожидание HTTP/планировщика, а `promptEvaluationSeconds` и `outputEvaluationSeconds` разделяют стоимость входа и генерации. `dataCharacters` показывает размер только полезного кадра, а `promptCharacters` — его размер вместе с системной инструкцией.

Базовый критерий для текущего CPU-профиля: на прогретой модели стремиться к `dataCharacters < 700`, `promptTokens < 700`, отсутствию `failed/stale` и wall-clock задержке менее 90 секунд. Это диагностическая цель, а не гарантия для другого процессора или модели.
